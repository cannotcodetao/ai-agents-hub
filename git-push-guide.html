GitHub 仓库创建与代码上传 SOP

四阶段标准流程：创建远程仓库 → 本地初始化 → 关联远程 → 推送上传。 附带日常更新流程、5 类常见报错的标准化修复、配置清单与命令速查表。

§0 全流程速览

从零到代码出现在 GitHub 上，一共 4 个阶段。照着做一遍即可，全程约 5 分钟。

阶段一 · 线上操作

① 创建 GitHub 远程仓库

在 GitHub 网页建一个空仓库，拿到它的 HTTPS 地址。

→ §1 创建 GitHub 远程仓库

阶段二 · 本地操作

② 本地初始化仓库

在项目根目录执行 git init，先写好 .gitignore，产生第一个提交。

→ §2 本地初始化仓库

阶段三 · 连线

③ 关联远程仓库

用 git remote add 把本地仓库和刚建的 GitHub 仓库连起来。

→ §3 关联远程仓库

阶段四 · 上传

④ 推送到 GitHub

git push -u origin main，刷新网页即可看到代码。

→ §4 推送到 GitHub

ⓘ
仓库已经建好了、只是想同步新改动？ 直接看 §5 日常更新流程 —— 4 条命令搞定，不必重走上面四个阶段。
⚠
动手前先确认两件事：
  1. 网络能连上 GitHub（内地需要代理，配置见 §6-1）
  2. .gitignore 已写好 —— 别把依赖目录、构建产物、密钥文件、个人隐私材料传上去（见 §2 步骤 2）

§1 阶段一 · 创建 GitHub 远程仓库

全程在浏览器完成，不需要命令行。前提：已注册并登录 GitHub 账号。

1

打开新建仓库页面

访问 https://github.com/new。

2

填写仓库名与可见性

  • Repository name：用英文/数字/短横线，建议与本地项目文件夹同名（如 my-project）。
  • Description：可选，一句话说明用途。
  • Visibility：Public 公开 / Private 私有。 含隐私材料（简历、客户数据、内部资料、密钥）一律选 Private。
3

不要勾选任何「初始化」选项（关键）

下面三项全部留空：

  • ☐ Add a README file
  • ☐ Add .gitignore
  • ☐ Choose a license

原因：勾选后远程仓库会自带一个提交，与本地历史无共同祖先。首次 push 会被拒绝，需要多做一步处理（见 §6-2）。建一个纯空仓库可以让上传一次通过。

!
已经勾选了、或仓库是别人/自动生成的，不用删仓库重建 —— 直接按 §6-2 的两种策略之一处理即可。
4

创建并复制仓库地址

点 Create repository，然后在仓库首页点绿色 Code 按钮，切到 HTTPS 标签，复制形如下面的地址（下一步要用）：

https://github.com/<你的用户名>/<仓库名>.git

想用 SSH 免密方式，同位置切到 SSH 标签，复制 git@github.com:<用户名>/<仓库名>.git，配置见 §6-4。

✓
阶段一完成标志：GitHub 上能看到这个空仓库页面，并已复制好仓库地址。

§2 阶段二 · 本地初始化仓库

在项目根目录打开 PowerShell 或 Git Bash（Windows 下先进入项目文件夹，可在文件夹里右键「在终端中打开」）。 路径示例：D:\path\to\your-project

前置 · 一次性全局配置（新环境才需要，已配过可跳过）

# 1. 身份信息（GitHub 依据邮箱把你的提交关联到账号）
git config --global user.name  "你的GitHub用户名"
git config --global user.email "你注册GitHub的邮箱"

# 2. 换行符（Windows 推荐）
git config --global core.autocrlf true

# 3. 默认分支名 main
git config --global init.defaultBranch main

# 4. 凭据管理器（记住 GitHub Token，避免重复输入）
git config --global credential.helper manager

# 5. 代理（内地网络需要，端口按你实际代理软件填）
git config --global http.proxy  http://127.0.0.1:7890
git config --global https.proxy http://127.0.0.1:7890

# 6. HTTP 缓冲（可选，防大仓库推送中途断开）
git config --global http.postBuffer 524288000

检查当前全局配置是否已生效：

git config --global --list

步骤 1 · 初始化本地仓库

1
git init -b main

成功提示：Initialized empty Git repository in .../.git/； -b main 表示把默认主分支命名为 main（与 GitHub 默认一致）。

ⓘ
如果目录里已经存在 .git 文件夹，说明已经是仓库了，跳过本步，直接从步骤 2 开始。

步骤 2 · 先写 .gitignore（务必在 add 之前）

2

在项目根目录新建名为 .gitignore 的文件，列出「永不入库」的内容。

⚠
顺序很重要：必须先写好 .gitignore 再执行 git add。 文件一旦被提交，即使之后补进 .gitignore，它仍然留在历史记录里，需要额外操作才能清除。

下面是一份可直接使用的通用模板（按需增删）：

# ---- 依赖目录 ----
node_modules/
.venv/
venv/
__pycache__/
*.py[cod]

# ---- 构建产物 ----
dist/
build/
out/
target/
*.egg-info/

# ---- 密钥与环境变量（务必忽略）----
.env
.env.*
!.env.example
*.pem
*.key
*.authcode
config.local.json

# ---- 个人隐私材料（按需保留）----
resume/
简历/
attachments/*
!attachments/.gitkeep

# ---- 编辑器与系统 ----
.vscode/
.idea/
.DS_Store
Thumbs.db
desktop.ini

# ---- 临时文件 ----
*.tmp
*.bak
*.log
✕
绝不入库的清单： API Key / Token / 密码、.env、私钥文件、 真实个人隐私材料（简历、证件、客户名单）、大体积二进制与数据集。

步骤 3 · 暂存文件

3

三种方式按颗粒度需求任选：

# 方法 A（常用）：暂存所有改动 + 新增文件（自动遵守 .gitignore）
git add .

# 方法 B（精细）：只暂存指定文件或目录
git add src/main.js
git add docs/

# 方法 C（逐段确认，变更较杂时用）
git add -p

验证暂存结果：

git status --short

字母含义：A 新增 · M 修改 · D 删除 · ?? 未追踪（尚未 add）。

步骤 4 · 产生第一个提交

4
git commit -m "Initial commit"

预期输出：[main (root-commit) abc1234] Initial commit，后跟变更文件统计。

ⓘ
如果忘记加 -m 而跳进 vim 编辑器：按 Esc → 输入 :q! 回车退出（不保存）。正常写信息：按 i 进入插入模式， 写完按 Esc → :wq 回车保存退出。
✓
阶段二完成标志：git log --oneline 能看到至少一条提交，git status 显示工作区干净。

§3 阶段三 · 关联远程仓库

把本地仓库指向 §1 创建好的 GitHub 仓库。这一步只需做一次。

1

添加远程仓库，命名为 origin

把地址替换成 §1 复制到的那一个：

git remote add origin https://github.com/<你的用户名>/<仓库名>.git

origin 是远程仓库的默认别名，约定俗成用这个名字即可。

2

验证关联是否成功

git remote -v

预期输出（两行，URL 应完全相同）：

origin  https://github.com/<你的用户名>/<仓库名>.git (fetch)
origin  https://github.com/<你的用户名>/<仓库名>.git (push)

若只有一行或缺 (push)，说明配置有误，用 git remote remove origin 删掉后重做第 1 步。

常见调整

需求命令
改成 SSH 地址git remote set-url origin git@github.com:<用户名>/<仓库名>.git
换成另一个远程仓库git remote set-url origin <新URL>
解绑远程git remote remove origin
同一个本地仓库挂多个远程git remote add backup <另一个URL>，推送时写 git push backup main
✓
阶段三完成标志：git remote -v 输出两行且地址正确。

§4 阶段四 · 推送到 GitHub

把本地提交上传到远程。首次推送用 -u 绑定追踪关系，之后日常推送只需 git push。

1

执行首次推送

git push -u origin main

-u 即 --set-upstream：把本地 main 与远程 origin/main 绑定。绑定后，以后在该分支直接 git push 即可，无需再写参数。

2

首次推送需要身份验证

GitHub 早已不支持账号密码，必须用 Personal Access Token（或改用 SSH）。弹窗时：

  • 用户名：你的 GitHub 用户名
  • 密码：粘贴 Token（以 ghp_ 开头），不是 GitHub 登录密码

Token 的创建步骤与免密方案见 §6-4。

3

确认推送成功

预期输出：

To https://github.com/<你的用户名>/<仓库名>.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.

然后刷新 GitHub 仓库页面，应该能看到全部文件。

本地再次核对：

# 本地 HEAD 与远程 main 的哈希应完全一致
git rev-parse main
git ls-remote origin main
!
push 被拒（fetch first / non-fast-forward）？ 说明远程已有本地没有的提交。按 §6-2 选择处理策略。

§5 日常更新流程（仓库已存在）

仓库已经建好、也绑定过远程，之后只是改了东西要同步 —— 4 步完成。

1

查看当前状态

先看一眼改了什么，避免误提交临时文件或密钥。

git status
git diff

status 看文件清单，diff 看逐行改动。若显示 nothing to commit, working tree clean，说明没有改动，无需继续。

2

暂存改动

git add .
git status --short
3

创建提交

git commit -m "类型: 简洁说明（动词开头）"

推荐的提交信息前缀（便于回溯定位）：

前缀含义示例
feat新功能feat: add export to CSV
fix修复缺陷fix: handle empty input
docs文档docs: update setup steps
refactor重构（不改行为）refactor: extract parse util
perf性能优化perf: lazy-load list data
test测试test: add unit tests for utils
chore构建/依赖/工具chore: bump dependency versions
4

先拉后推，然后推送

推送前先拉一次远程，避免与别人的提交冲突：

# 拉取远程最新（有冲突在本地解决，见 §6-3）
git pull --rebase

# 推送
git push

§6 常见问题与标准化修复

按报错信息找到对应编号，直接复制修复命令。

问题 1 · 443 连接失败 / 超时

报错信息：

# 典型报错 1：完全连不上
Failed to connect to github.com port 443 after 21000 ms: Could not connect to server

# 典型报错 2：连上但传输中断
RPC failed; curl 55 Send failure: Connection was reset
send-pack: unexpected disconnect while reading sideband packet

原因：内地网络无法直连 GitHub，且 git 不会自动使用浏览器的代理通道，必须单独为 git 配置代理。

修复：给 git 单独配置代理

# ① 配置 git 全局代理（端口填你实际代理软件的值）
# Clash / V2Ray 默认 7890 · Shadowsocks 默认 1080
git config --global http.proxy  http://127.0.0.1:7890
git config --global https.proxy http://127.0.0.1:7890

# ② 加大 HTTP 缓冲（大仓库推送防中途断开）
git config --global http.postBuffer 524288000

# ③ 验证是否生效
git config --global --get https.proxy
# 预期输出: http://127.0.0.1:7890

取消代理（不用代理 / 已回国时）

git config --global --unset http.proxy
git config --global --unset https.proxy
ⓘ
诊断技巧：git ls-remote <仓库URL> 能列出远程分支哈希，说明网络与认证都正常；若卡住或报 443，就是代理问题。

问题 2 · push 被拒：fetch first / non-fast-forward

报错信息：

! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/xxx/xxx.git'
hint: Updates were rejected because the remote contains work that you
hint: do not have locally.

原因：远程存在本地没有的提交 —— 常见于建仓时勾选了 README/.gitignore，或远程被其他人/平台初始化过。 先确认双方关系：

# 拉取远程引用但不合并，先看清楚
git fetch origin
git log origin/main --oneline -10

# 检查是否存在共同祖先（无输出 = 两条历史完全无关）
git merge-base main origin/main

两种处理策略：

策略命令适用场景
A. 合并（安全） git pull origin main --rebase
若提示 unrelated histories：
git pull origin main --rebase --allow-unrelated-histories		 远程有有价值的文件（README / LICENSE / CI 配置），想保留双方内容。可能需要解冲突，见 §6-3
B. 本地覆盖远程 git push --force-with-lease origin main 远程只是占位/废弃内容，本地才是完整权威版本。远程原有文件会被替换
✕
永远不要用裸 git push --force。 它会无差别覆盖远程，可能抹掉别人的提交。 --force-with-lease 会在推送前检查远程分支是否被改动过，一旦别人有新提交就会拒绝，安全得多。

问题 3 · 合并冲突 Merge conflict

报错信息：

CONFLICT (content): Merge conflict in src/main.js
error: could not apply abc1234... 你的提交说明
hint: Resolve all conflicts manually, mark them as resolved with
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".

手动修复步骤

  1. 打开冲突文件，找到三行标记： 
    <<<<<<< HEAD
本地当前分支的内容
=======
拉取下来的远程内容
>>>>>>> abc1234... 提交说明
  2. 把文件改成最终想要的版本，并删掉这三行标记。
  3. 保存后执行： 
    # 标记该文件冲突已解决
git add src/main.js

# 继续 rebase 流程（若是 merge 流程则用 git commit）
git rebase --continue

# 完成后推送
git push

批量冲突解决技巧（明确知道保留哪边时）：

# 以本地版本为准（保留我方）
git checkout --ours src/main.js

# 以远程版本为准（保留对方）
git checkout --theirs src/main.js

# 然后 git add + git rebase --continue
ⓘ
想放弃这次合并、回到操作前：git rebase --abort（rebase 流程）或 git merge --abort（merge 流程）。

问题 4 · 认证失败 Authentication failed

报错信息：

remote: Support for password authentication was removed on August 13, 2021.
fatal: Authentication failed for 'https://github.com/xxx/xxx.git/'

原因：GitHub 自 2021 年起不再接受账号密码，必须使用 Personal Access Token 或 SSH 密钥。

方案 A · 使用 Personal Access Token（HTTPS 方式）

  1. 打开 github.com/settings/tokens
  2. 点 Generate new token → 选 Tokens (classic)
  3. Note 填用途描述；过期时间按需；勾选 repo 权限（整组）
  4. 生成后立即复制（以 ghp_ 开头，只显示这一次）
  5. 下次 git push 提示输入时：
    • Username：你的 GitHub 用户名
    • Password：粘贴 Token（不是登录密码）

让 Windows 凭据管理器记住它，避免反复输入：

git config --global credential.helper manager
!
Token 等同于密码：不要写进代码、不要提交进仓库。泄露了立即到上面的页面 Revoke 撤销。

方案 B · 改用 SSH（一次配置，长期免密）

# 1. 生成 SSH 密钥（-C 填你的 GitHub 注册邮箱）
ssh-keygen -t ed25519 -C "you@example.com"
#    连续回车使用默认路径与空密码

# 2. 查看公钥全文并复制（Windows 路径）
type %USERPROFILE%\.ssh\id_ed25519.pub

# 3. 粘贴到 github.com/settings/keys → New SSH key

# 4. 把当前仓库的远程地址改成 SSH 形式
git remote set-url origin git@github.com:<你的用户名>/<仓库名>.git

# 5. 测试连通（首次询问 yes/no，输入 yes）
ssh -T git@github.com
# 成功提示: Hi <用户名>! You've successfully authenticated...

问题 5 · LF / CRLF 换行符提示

提示信息：

warning: LF will be replaced by CRLF the next time Git touches it

这不是错误，只是信息提示。原因：Windows 默认 CRLF，Linux / GitHub 默认 LF，git 自动转换。

想消除提示（推荐设置）：

git config --global core.autocrlf true

含义：检出时 LF → CRLF（适配 Windows 编辑器），提交时 CRLF → LF（保持仓库内统一为 LF）。

§9 附录 C · 推荐工作流

养成这套习惯，可以避免绝大多数冲突与误提交。

# ━━━ 动手写之前 ━━━
# 1. 先拉远程最新，保证起点是最新的
git pull --rebase

# ━━━ 写代码 …… ━━━

# ━━━ 准备提交 ━━━
# 2. 检查改动，防止误提交临时文件 / 密钥 / 日志
git status
git diff

# 3. 暂存 + 提交
git add .
git commit -m "feat: 明确的、动词开头的说明"

# ━━━ 推送前再拉一次，防止他人已推送 ━━━
# 4. 拉最新，若有冲突在本地解决（见 §6-3）
git pull --rebase

# 5. 推送
git push
★
核心原则 3 条：
  1. 先拉再写，再拉再推 —— 冲突永远在本地解决，不要带到线上。
  2. 小步提交，信息清晰 —— 半天几百行改动堆在一个 commit 里，之后无法定位问题。
  3. push 前看一眼 diff —— 能挡住绝大多数误提交（临时调试代码、密钥、日志文件）。

通用 SOP · 适用任意本地项目 · 命令基于 Git 官方 CLI（Windows 环境）
